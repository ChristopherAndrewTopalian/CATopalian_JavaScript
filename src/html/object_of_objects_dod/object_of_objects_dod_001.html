Data-Oriented Design (Separating Logic from Data)

As our simulations grow to handle thousands of entities, we must optimize for CPU and memory efficiency. A common mistake is to place active functions (Methods) directly inside our ship objects. While this seems organized, it creates massive memory bloat because the computer must duplicate the function's code for every single ship we spawn.

To achieve maximum engine performance, we use Data-Oriented Design (DOD). We keep our Object registries as pure, "dumb" data, and we write centralized, standalone functions (Systems) to process that data. You feed the ship into the engine, the engine modifies the ship, and the simulation continues at lightning speed. 

// THE DATA: A Pure Factory Function (No Methods)
function createStarship(shipName) {
    return {
        name: shipName,
        shields: 100,
        status: 'Active'
    };
}

// THE SYSTEM: A Centralized Logic Engine
// This function exists only once in memory, but can process any ship
function applyDamage(shipObject, damageAmount) {
    shipObject.shields -= damageAmount;
    
    if (shipObject.shields <= 0) {
        shipObject.shields = 0;
        shipObject.status = 'Disabled';
        console.log("ALERT: " + shipObject.name + " has been disabled!");
    } else {
        console.log(shipObject.name + " shields holding at " + shipObject.shields + "%");
    }
    
    return shipObject;
}

// THE SIMULATION: Passing Data through the System
let starfleetDatabase = {};
starfleetDatabase.defiant = createStarship('Defiant');

// Feed the pure data object into the central damage system
applyDamage(starfleetDatabase.defiant, 40);
applyDamage(starfleetDatabase.defiant, 70);

/*
Defiant shields holding at 60%
ALERT: Defiant has been disabled!
*/

Syntax 

function centralSystem(dataObject) { /* modify and return data */ }

Return Value

Type: Mutated Object (The centralized function processes the incoming Object and applies mathematical updates directly to its properties).

Description:

This functional approach is the secret to high-scale game architecture. By separating your "State" (the data) from your "Logic" (the functions), your CPU cache can read the data significantly faster. Furthermore, if you need to update how damage is calculated, you only have to rewrite one single function in your entire codebase, rather than worrying about the internal structures of thousands of active objects. It keeps the engine modular, readable, and highly optimized.
